# ADR-0007：Seata 要不要上？怎么上？

- 状态：Accepted
- 日期：2026-07-16

## 背景

微服务拆分后会出现「下单写订单库 + 扣库存库」这类跨服务写操作。业界常见两派：

1. **Seata（AT/TCC/Saga）** 追求近似 ACID 或编排补偿  
2. **Outbox + 消息最终一致** 接受短暂不一致，靠幂等与对账收敛  

拼多多社招面试里，**两套都要能讲清**；工程上不能「全家桶默认开 Seata」。

## 决策

### 默认（全局）

**不需要**把 Seata 作为所有跨服务写的默认方案。  
主路径继续：**本地事务 + Outbox → Kafka + 消费幂等 + 对账**（见 ADR-0006）。

### 局部引入（必须做，含金量）

在 **P6 微服务阶段** 落地 **一个** Seata AT 试点场景，用于对比与面试：

| 试点场景 | 参与服务 | 说明 |
|----------|----------|------|
| 普通下单：创建订单 + 库存占用 | Trade + Inventory | 短事务、同步、失败可回滚；最适合讲 AT |

明确 **不用 Seata** 的场景：

| 场景 | 原因 |
|------|------|
| 秒杀扣 Redis + 异步建单 | 要吞吐；锁与回滚会拖垮大促 |
| 拼团成团通知、关团退款 | 长流程，适合事件编排 |
| 支付回调后下游通知 | 外部渠道不可被 RM 管理 |
| Embedding / 搜推 / 埋点 | 旁路，最终一致即可 |
| 跨多个营销+支付+售后的长链路 | AT 锁持有时间过长，易雪崩 |

### 模式选择（已定）

- 试点用 **Seata AT**（上手快、能讲 undo_log / 全局锁）  
- **TCC / Saga** 不强制落地代码；在文档与面试中对比讲清适用边界即可  

## 备选方案

1. **全链路 Seata**：开发省事假象，大促与长流程必踩锁与运维坑 → 拒绝  
2. **完全不用 Seata**：工程上可行，但面试少一块「强一致中间件」实战 → 本项目用「默认不用 + 一处试点」补齐  

## 后果

- 正面：有真实 Seata 配置/踩坑经验；能对比 AT vs 最终一致  
- 负面：多一套 TC（Transaction Coordinator）运维；试点链路要压测锁冲突  

## 验证方式

1. 试点链路：Inventory 故意失败 → 订单侧回滚，无脏订单  
2. 同场景用 Outbox 版与 AT 版各跑一轮，对比延迟与失败率（写入压测报告）  
3. 面试能讲：全局锁、脏写、TM/RM/TC、为何秒杀不用 AT  

## 落地清单（挂在 P6）

- [ ] 部署 Seata Server（Compose）  
- [ ] Trade / Inventory 接入 AT；建 `undo_log`  
- [ ] 仅 `placeOrder` 普通下单开 `@GlobalTransactional`  
- [ ] 秒杀/拼团/支付回调路径确认 **无** 全局事务注解  
- [ ] ADR 实测笔记：超时、重试、锁冲突各一例
