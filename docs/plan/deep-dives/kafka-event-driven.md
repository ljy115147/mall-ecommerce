# Deep Dive：Kafka 事件驱动与可靠性

## 1. 为什么用 Kafka 而不是 RabbitMQ

| 维度 | 本项目选择 Kafka 的理由 |
|------|-------------------------|
| 多消费者独立进度 | 行为流同时服务推荐、数仓、风控 |
| 峰值削峰 | 秒杀命令堆积可水平扩消费者 |
| 可重放 | 对账、重刷索引、重算特征 |
| 分区有序 | 同 orderId 分区内有序，利于状态推进 |
| 生态 | Canal/Flink/数仓连接器丰富 |

代价：无原生灵活路由/延迟队列；运维与语义更重。关单用 Job+事件弥补。

## 2. 投递模型：Outbox

```text
业务事务 {
  写业务表
  写 outbox_event(status=NEW)
}
Relay {
  读 NEW → send Kafka → mark SENT
  失败保留 NEW/FAIL 可重试
}
Consumer {
  幂等处理后落库
}
```

面试必讲：先发消息再提交事务会导致「有消息无数据」。

## 3. 消费语义

- Kafka 提供 at-least-once（常见配置下）
- 业务层：`idempotent_record` 或唯一索引（biz_no）
- 需要顺序：同一聚合 key 进同一分区；消费者单线程分区内处理或细心锁

## 4. 秒杀命令 Topic 设计

- 高分区；key 可选 userId（打散）或 skuId（同 SKU 有序，可能热点分区——通常秒杀更关注吞吐打散）
- 消费者组独立；扩容水平加实例
- 失败进 DLQ；告警；可重放

## 5. 延迟关单为何不用「假延迟队列」

线上常见做法：

1. 订单写 `pay_deadline`  
2. 扫描到期（分片扫、翻页、记住游标）  
3. 发关闭命令事件  
4. 关单逻辑幂等，并处理与支付回调竞态（乐观锁状态 CAS）

优点：可补偿、可观测、不依赖 Broker 延迟插件。

## 6. Lag 治理

- 分级：预警 / 严重 / 事故  
- 手段：扩容消费者、优化处理、临时丢弃非关键（行为）、熔断上游生产  
- 面试讲一次真实 Lag 拉高的排查路径
