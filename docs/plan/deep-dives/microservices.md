# Deep Dive：微服务拆分与治理

## 1. 何时拆

满足再拆：

- 模块边界稳定（表不再来回挪）  
- 有独立扩缩诉求（秒杀消费、AI、商品读）  
- 团队/发布节奏需要隔离（即使一人，也按「虚拟团队」练）  
- 可观测与对账已能抓住一致性问题  

## 2. 数据拆分铁律

- 一服务一库  
- 禁止跨库 join  
- 跨服务数据：API 或事件复制（只读视图）  

## 3. 分布式事务立场（已定）

详见 [ADR-0006](../adr/0006-eventual-consistency-default.md)、[ADR-0007](../adr/0007-seata-scoped-usage.md)。

| 策略 | 用在哪 |
|------|--------|
| **默认** 本地事务 + Outbox + Kafka | 拼团、秒杀异步、支付后通知、搜推、绝大多数跨服务 |
| **局部** Seata AT | 仅试点：普通下单写订单库 + 库存占用（短、同步、可回滚） |
| TCC / Saga | 代码不强制；面试对比「长流程补偿」时口述 |

**为什么不是“上了微服务就必须 Seata”？**

1. AT 靠全局锁 + undo_log，热点 SKU、长事务会放大阻塞与回滚风暴。  
2. 秒杀/行为流要的是吞吐与削峰，不是跨库 ACID。  
3. 支付渠道、LLM、ES/Milvus 等外部系统进不了 Seata 资源管理器。  
4. 线上大量电商核心其实是 **账实最终一致 + 对账**，不是全程 XA。

**面试怎么讲才加分**：先说默认最终一致与对账，再出示「我在下单占用库存上真实接过 Seata AT，并测过锁冲突/回滚，所以知道它不该铺全站」。

典型最终一致：

- 下单占用成功 → 发事件 → 搜索/推荐旁路更新  
- 支付成功 → 事件 → 积分/消息（若有）  

## 4. 治理清单

| 能力 | 组件 |
|------|------|
| 注册配置 | Nacos |
| 入口 | Gateway |
| 调用 | Feign + 超时 |
| 限流熔断 | Sentinel |
| 灰度 | Gateway 谓词 |
| 追踪 | SkyWalking |

## 5. 故障隔离演示脚本

1. 正常下单成功  
2. `kubectl scale ai --replicas=0`（或停容器）  
3. 再次下单成功；客服/语义搜降级  
4. 恢复 AI
